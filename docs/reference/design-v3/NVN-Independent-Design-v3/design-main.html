1. 上一版确实有会影响实现的疏漏

上一版“静态检查通过”仅证明清单、引用和局部合同，没有证明整个系统可以直接照着实现。第三轮按真实失败时序和源码调用链重新审阅，发现并修订了这些关键问题：

  • 只有writer不够：必须跟踪未完成reader和tentative reservation，处理RAW/WAR/WAW；但WaitEvent polling不能进入会阻塞SignalEvent的普通reader集合。
  • copy不是万能退路：两个可写别名各做一份shadow，会破坏同一draw内的读写/atomic关系。必须保持共同物理表示，否则拒绝该快路。
  • submit失败不是全没执行：已接受前缀、未尝试后缀、接受性未知、fence导出失败分别记账；禁止整体回滚或重复提交。
  • 对象generation不等于ABI正确：真实SDK对象大小、inline字段、command用量计数均有跨游戏反例。候选头里的sizeof和返回类型不能不经核实就生成shim。
  • KGSL文件不能单独成为驱动：同Mesa DSO内新增桥接导出，复用完整的冷初始化/析构链，必须维护BO/VMA/fd所有权及WSI真实fence。
  • native descriptor不是统一64B对象：A6/A7 bank数量有限、graphics stage共用bank，某些SSBO占两个64B槽；shader编译以后还需要linkage、VFD/SP和const配置。
  • sysmem不自动排除并发binning：首个可核验基线显式关闭该模式，Query/Event作为明确执行边界。
  • 跨pool alias、跨extent MapEpoch、cacheline、raw CPU读与部分写：均补齐具体身份来源、事务和失败路径，不再用几个opaque字段代替算法。

各项审计包含原文位置、反例、修正及测试；不是宣称这些都是已在设备上复现的bug。

4. 本版固定的实现选择

  • native冷启动与配对销毁复用当前Turnip内部构造；公开逐draw Vulkan对象/命令转换不进入主路径。
  • 首个device backend只用普通BO、单真实queue、offscreen、单sample RGBA8、sysmem、VS/FS，之后独立CS；禁止并发binning。depth、多附件、GS/tess/XFB、复杂feedback均按明确增量能力加入。
  • NVNN_ADRENO_ABI_1采用4个bank，256B root和明确的stage/slot索引；具体硬件大小、索引单位、UBO/SSBO边界见gpu-execution-contract。
  • 全表snapshot只是正确性基线；约2300次变化draw若每次复制18.25KiB，会写约41MiB/frame。该条件算术不是性能结果，更不是推荐的终态。必须记录真实dirty分布；普通KGSL不存在免费的不连续页COW。
  • 用户应用的guest对象和GPU地址都不直接等同host C对象/指针。私有typed-v1可实现并测试，但真实D2R准入还要证明inline读写与Copy/descriptor/FenceEpoch的消费合同。
  • unknown userptr alias、未封口raw command patch、未支持CPU/GPU atomic域等明确拒绝，不能静默造shadow或假no-op。

CPU 优先：原生 NVN 验证线的收益预算与判据

0. 定位与直接结论

这是独立实验线的设计，不是开工授权，不要求修改现有项目、创建 PR、部署驱动或执行设备测试。本节所列测试均为未来实验设计；既有文档中的 host 正确性模型不是性能实测。

原生路径有降低 CPU 翻译负担的机会，但目前证据不足以承诺“省一半”或“省十毫秒”。仅把 Vulkan 调用改成 GPU 发包，不会自动消除 NVN 资源解析、物理版本管理、依赖、着色器语义转换和生命周期工作。更大的机会来自同时改变这些工作的表示与消费方式。 因此本验证线的首要成果应是：同一语义工作负载下，完整 NVN CPU 工作量下降，而不是首先展示 TBDR 带宽下降。

首选 Adreno / KGSL 是工程验证路径选择，不等于已经证明它比 PanVK 的 CPU 收益高。

2. 两条不同的收益假设

A. 只替换 Vulkan 后半段

保留现有逐 draw 资源消费、物理解析和依赖逻辑，仅将 Vk 对象交付改为原生描述符/寄存器/命令流。可以减少 API 对象约束、某些重复编码与驱动状态处理，但 CPU 还必须生成有效硬件状态、保活资源并提交。7.09–8.86% 不是其可删除预算，且可能漏掉分散在前端的 API 适配工作。

用一个明确反事实展示量级：假设该驱动包络与所比较窗口一致，并且其中一半能被净消除，则全线程节省约 3.55–4.43%；不是原生路线的预测，也不是原生路线总收益上限。这说明“少一层 API”本身不能解释从约 27ms 到 16.7ms。

B. 重做 NVN 资源消费表示，再直接输出原生状态

真正值得验证的热路径是：

  1. 资源注册/重建时生成长寿命硬件视图和访问 recipe；使用稳定 slot、generation 与物理版本标识。
  2. 绑定变更时更新局部状态；draw 时消费程序实际需要的 slot，不重新发现资源拓扑，不为已证稳定的集合重走全表。
  3. 对变化的 publication/map/alias/物理版本做定向失效；只复用“解析结果”，不跳过新写入的可见性、WAR/RAW/WAW 或在途寿命判断。
  4. 将已解析结果直接用于 native descriptors / state fragments，避免再构造一轮 Vulkan layout、set 组合和驱动状态镜像。
  5. 可重用录制片段必须带有效性依赖和完成后退休合同；不能把“上一帧相同 handle”当作有效性证明。

这条路线可能跨越 binding、planning、view 消费和 driver 等多个子树，因而潜力不受单个 vkCmd 调用时间限制。但当前尚无互斥归因证明可净删多少；不能把各 inclusive 子树求和，更不能预支全部资源消费成本。

3. 条件预算，不是承诺

令 p 为互不重叠且实际受改造影响的 CPU 份额，r 为该份额的净削减比例，h 为新增工作占原总 CPU 的比例：净节省 = p × r − h。

这里的 20/30/40% 是敏感性分析输入，不是源码或火焰图已证明的可削减份额。任何全量 root 拷贝、新增失效扫描、双份状态维护和提交调度都计入 h。

在旧受控场景约 27ms 的示例基线上，净省 10/20/30% 分别成为 24.3/21.6/18.9ms；达到 16.7ms 需净省约 38.1%。这些是算术，不是将不同窗口的采样百分比兑换为实测毫秒。后来持续测试的自适应分辨率、驻核与时钟不同，不能拼接成同一基线。

CPU Running 下降也不直接等于 FPS 同比上升：原游戏/worker、GPU 和等待可能转成瓶颈。其他线程累计 CPU 不可与翻译线程 Running 相加充当串行帧时间。

4. 当前 GPU ABI 必须暴露的 CPU 风险

gpu-execution-contract.md 的 Bank 3 正确性基线为 289 × 64 字节有效表，对齐分配 18,688 字节，即 18.25KiB。若每个变化 draw 都完整复制，在假设每帧 2,300 次的条件下，单这一项就是 42,982,400 字节/帧，约 41MiB/帧；60 帧目标时约 2.4GiB/s 的 CPU 复制载荷，尚未包括分配、缓存污染、哈希和元数据。

这不是已观测流量，也不代表每 draw 必须复制，但足以说明：删 Vulkan descriptor 更新，再引入整张 native 表快照，完全可能得不偿失。

首个 CPU 有效版本应优先验证：

  • 未变化表版本直接复用；root 内容变更不导致无关 UBO/SSBO 表全量重编码。
  • 区分 root 数据页与描述符表；root 指针变化造成的 index0 更新也需要版本化，不能原地改 GPU 在途表。
  • 明确统计快照字节、实际 descriptor 编码条数、root 发布字节和存活版本数。
  • 若做 per-program 紧凑布局/重新分 bank，作为显式 ABI 版本与 IR3 链接方案审核；不能只在文档中声称“增量”而物理上仍 memcpy 18.25KiB。
  • 不依赖未证明的 GPU 虚拟页 COW。普通 KGSL BO 的连续布局与在途可见性约束依然存在。

5. CPU 优先的实验设计与停止条件

以下是设计规格，不表示已实施或运行。

第一关：同工作量、互斥归因

建立固定 NVN 语义轨迹和初始资源快照，固定 shader 版本、画质、draw/dispatch、数据发布及提交边界。旧 Vulkan 与 native 路径分别统计：解析/解码、资源消费与失效、依赖与生命周期、绑定编码、pipeline/state 编码、提交及同步。单独记录 native 新增工作，避免 inclusive 叠加。

优先指标：完整翻译线程 Running、cycles、instructions、每 draw CPU、完整帧 CPU；辅以时钟/驻核、runnable/wait、系统调用和缺页归因。缓存命中率及某函数 SELF 下降只作解释指标。

第二关：先证明 CPU 结构收益，再增加 tile 调度复杂度

先让 Adreno 原生路径采取明确受控的 sysmem 渲染策略，记录实际 binning 模式，不能误将 sysmem 等同于绝无 binning。保留正确依赖、缓存管理和图像转换；对照完整 Vulkan 工作量，不通过删除语义工作制造低 CPU。

纯 host 发包/录制回放可以隔离前端编码成本，但不验证 GPU 执行正确性、cache 行为、图像布局或真实端到端速度。只有硬件对照才能给出端到端结论。

第三关：防止搬家与隐性膨胀

同一轮比较必须报告：CPU 时间与指令；根表/描述符实际写入字节；BO/快照版本及峰值；command bytes；实际 draw 数；cache flush/wait 次数；图像转换及回读字节；CPU→GPU 提交延迟与 GPU 时间。拒绝用缓存命中率、表示条数或单一父节点下降作为通过标准。

若只有驱动调用小幅变快，而资源消费总成本未降，结论应是“直接发包路线收益有限”，先检查长寿命表与定向失效，不立即加入复杂 GMEM pass 编排。若 GPU ABI 大表复制吃掉净收益，先修 ABI；若 CPU 已显著下降，再评估 tile 分组与 GMEM 保留的增量价值。

最终判据

验证通过应同时满足：同等语义/画质、完整 CPU 成本下降且跨重复窗口稳定、未以不可接受的 GPU 时间或峰值内存换取、正确性与生命周期合同通过。达到多少下降才值得继续，可以作为项目决策阈值单独设定；它不是预测值，也不应事后挑选最好窗口。

接入边界：通用 NVN 库、宿主适配与可选游戏策略

本文件回答“是不是必须给每个游戏写一堆hack”。目标是通用NVN兼容库＋薄宿主接入层，不是另造D2R专用渲染器。本次仅设计，不执行接入或开发。

1. 对外一对一，对内不逐条机械发包

库提供NVN函数名、函数调用ABI、对象布局profile、返回值和命令语义。游戏仍通过BootstrapLoader/GetProcAddress等入口取得函数，宿主把调用重定向到此库。setter可能只更新host字段，Bind记录规范化状态，若干draw可合成原生状态块/执行片段；一对一的是外部合同，不是GPU包数量。

正式库不能只覆盖函数名：SDK对象大小/inline字段、command memory可观察布局、shader二进制、texture pool和GPU地址都是兼容边界。v3已经将未知签名/布局列门禁，不能用524行清单代替已完整实现。

2. 宿主适配应按运行环境，不按每个游戏重复实现

拟定HostServices责任：

  • GuestAddressSpace：客体CPU地址访问、GPU虚拟地址与pool映射通知，不能将guest地址强转host指针。
  • HostAccess/Observer：CPU读写观察或显式lease桥；游戏合法CPU/GPU同步的发布边界。
  • GuestCallBridge：内存扩容callback的调用约定、当前guest线程上下文和重入约束。
  • SurfaceBridge：独立实验窗口/离屏目标、acquire/release与生命周期。
  • Diagnostics/Capabilities：错误、未支持语义、设备/ABI profile与资源预算。

NVN Program的NVIDIA shader到NIR/native编译链应属于通用库能力，不是每游戏重写shader的外置补丁。D2R离线shader包可用于首轮实验，但不能因此省去未来通用Program翻译的设计。

3. 两类宿主的接入成本不同

已在NVN API层截获

nxnative/D2R类原生运行环境或具有NVN HLE的模拟器，可以替换入口解析目标并提供HostServices。CPU架构/调用桥仍由宿主负责，库不承担CPU模拟。初次接入可能需按SDK版本识别入口，但不应为每个游戏改渲染器。

只在nvdrv/GPU提交层截获

传统低层GPU模拟器拿到的是Maxwell命令流而不是NVN调用。它不能仅加载本库就替换现有Vulkan backend。可选：

  1. 增加NVN HLE截获，转到本库；对直接提交GPU命令的路径另处理。
  2. 保留Maxwell method解码器，将其有序语义/资源映射接到本库执行层。

第二条是另一套前端，需要自己的decoder与语义映射，不属于本次首个NVN函数库验证版本。不能把两条路线的兼容范围混写。

4. 三种“特殊处理”要分开

类型例子是否基础能力放在哪里
正常NVN语义实现shader ISA转换、GOB/native布局、别名、同步、query是；不是游戏hack通用core/backend/compiler
二进制/SDK兼容profile对象inline字段、已知命令patch格式、handle编码某些调用者需要；应尽量版本化/通用化ABI/CommandStorageAdapter，严格匹配
游戏/质量优化native资产包、BC→ASTC、FXAA跳过、bloom降质、UI重放、外推否；不作为通用库的基础前提可选D2R adapter/quality profile

识别特定shader后做可证明等价的优化可以逐步泛化为IR模式pass；仅因游戏名就改变shader结果、删draw/barrier或伪query不是通用实现。raw command patch若最终有完整编码支持，也应从per-game模板迁到版本化decoder。

5. 实验中必须分别报告两种结果

  • 通用模式：不依赖D2R专用资源/画质hack，验证普通NVN调用、shader、资源与同步。
  • Qualified模式：显式启用native资源包或游戏策略，分别报告额外CPU/GPU/RAM收益和兼容限制。

仅第二种跑通，不能宣称通用NVN库已经成立。未来换一个符合已支持ABI和能力的游戏，应主要是宿主接线与兼容资格，而不是再写一套游戏渲染逻辑。

独立验证项目的实验阶段：Turnip/KGSL 窄闭环

本文件是单独开线的验证项目设计，不是现有项目的改造、PR、合并或实施授权。当前只修订设计文档；没有开始驱动开发或设备执行。若用户以后决定实施，应另行确认实验环境和范围。本文件替代第 08 章的阶段顺序，以及 revision2/turnip-strategy.md 的 T0–T2 含混边界。这里的路径和 nvnn_* 符号是拟新增实现，不是已存在或已验证的驱动接口。现存源码锚点以本包固定 revision 为准。此次只进行静态审查和设计，不提交驱动补丁、不运行设备。

1. 必须先纠正的计划错误

  1. 已找到公开 host import/native image 补丁，但其与 f830 产物的对应及设备资格仍阻断的是“既有 guest CPU 页面直接 import/native image”路线，不阻断普通 KGSL BO、host 状态机、离屏 clear/draw。不能把取得自定义驱动源设成所有工作的 T0。
  2. P1 同时要求 import、shader、descriptor、draw、compute、copy、fence、present，实际是一组独立风险，不能作为一个阶段。尤其 present 不应阻断离屏像素验收。
  3. “全部 523 调用都有行”不是 loadable frontend，更不是调用实现。未知返回 ABI 不能统一返回零；没有契约的入口不能被标为可执行。
  4. 首版不先建带 bind_gpuva 的通用后端虚表，不先抽取 Turnip/PanVK 共同调度器。KGSL 的 native BO/submit、Adreno shader/root、资源可见性直接实现一条路径；只共享已有 NVN 不变量和 host 测试。
  5. 高级画质/场景 hack 不能替代运行必需的同步或 query。首先需要不带这些 hack 的窄语义闭环；将其设置为默认开关会令后续结果无法归因。

2. 四个里程碑，不混称“能跑了”

层级严格含义不代表
L0 可加载前端ARM64 library 可被独立 harness 加载；已实现 resolver ABI、对象生命周期和录制测试通过；未知入口受控报错D2R 可以启动；任何 GPU 命令已正确
L1 离屏像素闭环同一原生 device/context 的 BO、提交、完成、读回通过；先 clear，再单 program triangle，像素参考正确已处理 NVN shader 二进制、GOB、游戏窗口
L2 D2R 小核心一份明确列出的实际调用/资源/shader 序列能重放；逐项满足实际 NVN 输入语义，输出、时间/事件和 CPU 可见内存正确一个游戏的全部场景，更不是整个 NVN
L3 D2R 场景闭环冷启动、流送、战斗、菜单、区域切换、退出恢复、surface 重建在冻结条件下通过；动态实际调用无缺项所有 523 名称的通用兼容

L0/L1 的测试程序必须标明 synthetic。只有消费真实 D2R NVN shader/调用/资源输入的测试才可标 L2。用手写 NIR triangle 不得标成“NVN shader 已完成”。完整 NVN 是独立持续兼容工作，不设置“一次补全 523 个入口”研究范围。

根表复制预算：正确基线不等于性能最优

GPU 合同的完整 bank3 snapshot 约 18.25 KiB。若每个 changed draw 都复制整表，2300 draw/frame 约 41 MiB/frame（约 43 MB），60 fps 仅 payload 写入即约 2.4 GiB/s，尚不含 cacheline 回写、读取与分配开销。这是条件上界算例，不是实测 D2R draw变化率或带宽。首版保守快照是正确性基线，不能预先称为最高性能方案。

V11 必须记录 changed-root 次数、root/table copy bytes、dirty stage/slot 分布和 CPU encode time。只要正常稳定绑定轨迹仍按 draw 复制完整表，视为未达到计划复用目标，应先检查 recipe/key 误失效；若确由合法参数高频变化造成，普通 KGSL BO 路径仍必须分配新的连续 bank/table 版本，可用模板和经证明的实际可达范围减少重建/复制工作，但不能把逻辑 stage 分页说成免费物理页 COW。进一步缩小表需要显式的新 ABI，例如按 program 压缩/rebanking，并同时修改 shader lowering、边界检查及缓存键；真正页级 COW 需要独立 VA/VBO 映射能力及组合资格，不是首版默认能力。所有版本保留 generation 和退休引用，不原地修改在途表。只有复制下降且 golden/消费时点负控不变才启用；引入间接层须同时衡量 shader dependent load 的 GPU 代价，不能只以 CPU copy bytes 判赢。

3. 不能用“保守 fallback”藏起来的问题

  1. unknown alias 若无法证明 backing 独立，不能造两份各自私有的 view copy：同一 draw 内两个 storage 地址的 atomic/读写交叠会立刻破坏语义。允许慢路必须维持共同物理身份/顺序，做不到则 unsupported。
  2. 消费时点未知不是“多等一会即可”：晚于应锁存时刻读取 descriptor/Sync 也可能读到错误版本。必须 oracle 或明确 profile 限制。
  3. GPU native write 后 CPU部分写无法仅凭旧 snapshot差分恢复；即使CPU写的值等于旧snapshot，也可能是在覆盖GPU新值。CPU取得写lease前物化当前字节并处理同cacheline ownership。
  4. unknown submit outcome 不能自动重试：同一 draw/atomic可能已执行，重复会改变结果。保留 receipt/refs直到可信终止或context销毁确认。
  5. 简化 shader不能作为不支持输入的fallback；clear/triangle演示与真实 NVN Program是不同等级。

4. 性能问题的明确决策规则

  • 是否先做 VBO：默认不做。先报告真实跨window slowpath次数、import页驻留、patch地址/额外copy时间。只有该项成为可观察主要成本且组合probe通过，才独立立项。
  • 是否先做 GMEM：默认不做。先完成同输入 native sysmem与reference对照，分离 CPU translation、GPU stall/bandwidth。CPU绑定未消除前不以GMEM掩盖热点转移；游戏目标所必需的 WSI 和 sysmem replay 资格先于 GMEM优化。
  • 是否保留 Vulkan 冷依赖：保留，不作为失败。第一目标是 hot draw不经 Vulkan对象和重复资源整理；后续只有维护/体积/启动成本证据足够，才拆冷初始化。
  • 是否保留 mprotect：不是二选一口号。受控API/lease可直接记发布；不受控CPU访问需经过经过验证的observer。没有完整 observer 不能仅为降低signal数关闭它。
  • 是否允许 D2R专用优化：可以，但必须是独立profile：输入manifest、资格predicate、失效动作、降级、独立计数和golden。场景名/上一帧行为不能独自成为正确性证明。

0. 范围与证据等级

这是拟新增实现规格，不把私有格式冒充 Nintendo 命令格式。证据索引及反例见 audit-api-recording.md。首个可构建目标是 host CPU library + fake backend；首个 device backend 只消费同一 IR。正式 NVN 函数入口和64位参数转发与内部格式分离。

建立两条明确 profile：

  1. typed-v1：只从拦截的API生成命令，64位command handle为不复用token；本文可立即实现、无需GPU。未知inline读写或native编码不能准入。不是“全部 NVN 已兼容”。
  2. raw-compat:<game-build>:<sdk-profile>：guest观察的对象字节、command字节、内存用量与patch模板逐项有证据。可沿用已验证的紧凑host记录模板，但不能宣称理解所有Maxwell包。native backend IR仅是派生缓存。

D2R初版以typed profile起步，静态使用优先加入；是否可用typed profile运行D2R须通过直接命令内存访问审计及运行写集资格，不因静态没有GetMemoryUsed调用就假定不存在inline访问。未知入口resolver拒绝并记录一次，不返回成功nop。

1. 文件/模块边界

  • frontend/abi_profile.{h,c}：目标ABI、对象允许写范围、inline字段、外部句柄编码、已资格枚举及错误返回策略。
  • frontend/object_registry.{h,c}：对象身份和生命周期，不知道GPU寄存器。
  • frontend/command_storage.{h,c}：命令/控制双arena、回调桥、预算和range tracker。
  • frontend/recording.{h,c}：API→内部记录，全部值参数验证及原子追加。
  • frontend/bytecode.{h,c}：typed验证/解码、raw profile adapter，禁止裸cast不可信字节为C struct。
  • frontend/command_cache.{h,c}：版本化IR块和反向依赖失效。
  • frontend/sync_state.{h,c}：FenceEpoch、EventRef、QueryEpoch和有序执行IR。
  • frontend/descriptor_view.{h,c}：执行消费视图，稀疏slot版本选择。

模块内部状态返回 NvnnResult（详细拒绝原因另列）；void NVN入口不能凭空返回错误值。适配层将失败转入该device的诊断/拒绝状态，阻止含半记录的handle提交；正式queue error输出ABI未知时不能写猜测大小的结构。

2. ABI profile 与对象 registry

AbiProfile 必填：profile_id、game_build、ptr_width=64、endianness=little、calling_convention、bool_width=1、enum_width=4、每对象minimum_known_extent及allowed_write_ranges、inline_field_rules、handle_policy、callback trampoline、supported entry signatures。

候选头的reserved[]大小只做来源信息，不能当真实guest分配大小。未确认范围默认零写入。API Initialize一般可以仅注册外部地址，不在guest内写host指针；需要SDK内联行为的profile由专门codec维护guest字节。禁止整个对象memset。禁止把+0x10未知字段拿来存end指针。guest栈对象也用registry，不依赖guest内host标记。

ObjectKey=(device_id,guest_address,kind)；ObjectRef=(registry_id,generation)。Record包括 Lifecycle、AbiProfileId、规范化host元数据、引用计数、retirement_set、可选guest inline mirror版本。Lifecycle为 UNINITIALIZED→LIVE→FINALIZING→RETIRED。Initialize同址新代数；kind不符、double init、失效引用受诊断。Finalize从lookup删除LIVE资格，原有已允许引用保留host记录至引用归零且全部queue points完成。

并非所有对象均延迟同样内容：Bind固定状态复制规范化值，故state对象可不持久引用；BindProgram固定 ProgramVersion；PoolRef/TextureRef等引用寿命按命令/descriptor所需保留。Finalize不是许可继续读取guest原对象的理由。shader control/data若异步编译，必须按已确定ProgramSetShaders消费合同保存所需字节/稳定storage引用，不只浅复制NVNshaderData指针。

ABI桥测试：小端uint64、负ptrdiff、count<0、NVNboolean低8位、单字段8字节struct句柄的调用约定、callback参数顺序、输出参数canary。不把host native typedef跨平台当guest ABI。

3. Recorder 状态机与双arena

Recorder字段：ObjectRef、state、owner_thread、callback_fn/data、callback_depth、command_arena、control_arena、recording_id、pending_record、error、budget_profile。状态 IDLE→RECORDING→IDLE；任意失败→POISONED；Finalize→DEAD。IDLE允许换arena/config；RECORDING允许Append/补arena/End；重复Begin、无Begin的End、DEAD调用拒绝。POISONED不能产出有效handle。

Arena字段：arena_id、generation、kind、guest_extent、cursor、usable_end、budget_origin、used_since_add、segment_list、storage_use_set。command存储关联PoolRef+logicalRange；control存储关联注册的CPU range。不得把GPUVA当CPUptr。所有offset/size/cursor加法先做overflow和containment检查，负offset直接拒绝。

typed-v1格式预算与native包预算完全独立。typed-v1 ControlRecord固定32字节，8字节对齐：u32 kind、u32 byte_size=32、u64 logical_owner、u64 target、u64 aux。kind=1是HandleManifest，End时收费一次；kind=2是跨segment link，换段时收费一次；kind=3是Call edge，每个被调handle一次。host IR缓存、native描述符缓存不向guest control预算重复收费。此收费是私有profile约定，不是NVN实测。

AddCommandMemory/AddControlMemory注册新的当前segment；不隐式释放以前segment。顶层Add从此重设对应budget_origin和used_since_add，已封存handle保留自己的segment manifest。RECORDING内因callback补充允许链接旧segment。raw profile需要重现其观察到的累计计数策略，不能直接沿用typed定义。任何在途仍使用的重叠存储覆盖，先检测非法复用，不通过代数掩盖。

Begin不分配synthetic BEGIN记录。End写8字节END，创建32字节control manifest并sealed handle；空录制也有合法END。Free返回物理可用剩余，appendable_free另扣链接保留，不混淆；Size/Used/Free的对外定义由profile固定。

Append事务：先规范化与复制临时值参数→计算两类需求→ensure_capacity→保留两arena区间→写payload→最后发布header和cursor。任何失败不发布半条记录；若callback已成功添加arena但记录失败，允许arena结构变化，不能声称全部API无副作用。Copy大块可多条原子提交但必须保持目标recording整体可回滚或poison，禁止输出半Copy的可执行handle。

4. 回调与线程规则

ensure_capacity以kind选择event0/1，size为该profile要求的最小补充量（含alignment和必要link reserve）；不能固定只发event0。保存当前fn/data快照，置callback_depth，释放registry/arena/queue锁，使用guest ABI trampoline同步调用。回调返回后重新lookup recorder代数和state，检测被Finalize/换对象，重新计算容量，不能继续使用旧host指针。

回调在同线程允许：AddCommandMemory、AddControlMemory、Get*Memory*、Get/SetMemoryCallbackData及profile允许的配置；禁止对同recorder Begin/End/Append/Finalize的递归GPU录制。其他recorder可独立录制。没有补足需求的回调返回视为无进展，返回OOM并poison，不固定重试两次掩盖错误、不无限重试。用户更换callback供后续exhaustion使用，不递归重试新callback。

每recorder单写者；不同recorder可并行。Registry可短锁；调用guest callback、backend wait、编译器时不得持有全局锁。Queue API用每queue线性化锁，实际等待在锁外。EventGetValue和CPU Signal采用资源同步合同，不能凭C volatile宣称线程安全。异步错误只锁存诊断，不能从driver工作线程重入guest callback。

5. typed-v1字节码与验证

所有多字节小端；记录8字节对齐。header为u16 opcode、u16 flags、u32 byte_length（含header，>=8且8倍数）。不得将其直接定义为外部NVN布局。opcode版本受profile id控制，未知opcode/flags拒绝；END长度8。payload中的引用为内部u64 registry token，绝不存C指针。每handle manifest记录profile_id、segment ids/epochs、范围、record_count、direct_ref_set、nested_call_edges、content_version和digest。

第一批opcode：END、CALL、BIND_STATE、BIND_PROGRAM、SET_DESCRIPTOR_POOL、BIND_DESCRIPTOR_SELECTOR、BIND_BUFFER、DRAW、DISPATCH、BARRIER、COPY_BUFFER、UPDATE_BUFFER、WAIT_SYNC、FENCE_SYNC、WAIT_EVENT、SIGNAL_EVENT、RESET_QUERY、REPORT_QUERY。枚举数值在单一generated internal header维护，不能沿用旧OP枚举ordinal碰巧相同。

具体payload：

  • CALL：u64 command_token；byte_length=16。数组API在返回前复制n个token，n=0不读数组；不保留数组指针。
  • BIND_DESCRIPTOR_SELECTOR：u32 stage、u32 slot、u64 selector；length=24。pool身份取命令执行state，不在这里冻结全部pool。
  • SET_DESCRIPTOR_POOL：u32 kind、u32 reserved、u64 PoolRefToken；length=24。
  • UPDATE_BUFFER：u64 address、u64 buffer_size、i64 offset、u32 data_size、u32 reserved、data[data_size]及零padding。data在录制前完整读取复制；length=align8(40+data_size)，所有求和范围检查。真实NVN的size/alignment限制由entry profile验证。
  • WAIT_SYNC：u64 SyncRefToken；length=16；入队实例解析为FenceEpochRef，不改原始封存记录。
  • WAIT_EVENT：u64 EventRefToken、u32 mode、u32 value；length=24。
  • SIGNAL_EVENT：u64 EventRefToken、u32 mode、u32 location、u32 flags、u32 value；length=32。不能丢loc/flags。
  • RESET_QUERY：u32 type、u32 reserved；length=16。
  • REPORT_QUERY：u32 type、u32 report_profile、u64 dstLogicalAddress；length=24。

bytecode验证先验证整个direct stream及范围，再解析对象refs和DAG；无递归C调用栈，迭代walker+显式frame stack。检测循环、超出manifest的JUMP、截断payload、整数溢出、重叠非法记录。深度/总展开量有profile上限和诊断，不写任意“16层就是NVN限制”。typed跨segment链接存在control manifest，不在客体字节里存裸指针。

6. Call、Copy、句柄与patch cache

typed-v1的Call捕获被调handle身份；执行按该handle当次准入的内容版本，不保存调用时整个资源内容。Copy复制来源直接记录及inline payload；对来源中CALL仅复制其引用边，不递归冻结被调块。内部可共享不可变块以省拷贝，但Copy目标的直接记录版本不能随源patch改变。Copy时确认来源完整sealed，锁定内容epoch，在复制完成前若被改写则重试一致快照或失败，不输出混合版本。

raw NVN Copy语义尚未资格。D2R临时准入可证明来源及传递调用集合在目标最后消费前不可变、存活且未重用，此时reference/copy观察等价；没有证明则拒绝该资格，不能默默沿用OP_CALL。源代码现有hacks不算证明。

typed句柄token全进程单调唯一（溢出停止）；FinalizeCommandHandle解除未来提交资格，已提交instance仍保留版本。raw句柄可能就是地址，地址本身不能区分ABA；profile规定重新录制旧存储前旧handle必须退出合法使用区间。同一个外部数值对应当前可见storage epoch，不允许猜测用户意图。

patch cache key=(profile,handle_id,content_version,backend_arch,resource_binding_abi)。dirty tracking依赖guest命令实际range，host写记录时更新同一版本。修改selector只invalidate对应block与依赖摘要，非全frame。raw LM3模板保持single-bind handle在+0x10；其他未知patch拒绝，不把其误读为count。提交时生成稳定解码版本及native batch，完成前保留旧版本；未来submit见新版本。guest与正在执行command字节的无序并发修改不在此机制中自动变合法，按原API race/同步合同验证。

7. 消费时点与描述符规则

四个时点：HOST(API当场)、RECORD(固化值)、ENQUEUE(队列线性化/版本选择)、GPU_ORDERED(实际执行读取)。不得把四者合并成“提交读取所有数据”。

  • setters/getters、callback配置：HOST。
  • fixed-state Bind、view参数数组、draw标量、handle数组、UpdateUniformBuffer源数据：RECORD。
  • program内容：按ProgramVersion消费合同固化所需编译输入；不浅拷贝指针后任意晚读。
  • vertex/index/indirect/SSBO/image字节、event值：GPU_ORDERED。
  • descriptor选择器：RECORD；其引用slot在已资格有序消费点解析；typed-v1 ENQUEUE选择提交视图，后续CPU更新必须排序到下一消费epoch。对于允许执行期间更新的正式NVN用法，此profile不够，需独立live-table协议，不伪装支持。

SubmissionDescriptorView包含(pool identity,generation,slot→DescriptorVersion)的稀疏映射、实际可达slots集合、GPU native root和retirement_set。没有全池poolSnapshot，也没有每draw复制整个pool。register预编码候选描述符；只有存在在途冲突时复制受影响native页/槽。没有冲突原地更新+必要cache invalidate。旧提交保持旧native页，后续提交选择新版本。shader动态索引证明不了可达集合时保护该绑定池允许范围，并记录成本，不只保护绑定的单个slot。

缓存命中仍登记本次访问依赖、map epoch、publication依赖和ticket。若槽内容未改但纹理内容变了，描述符编码可以复用，资源可见性依然重新纳入图。

8. Sync/Event/Query执行实例

SyncObject={ObjectRef,state:UNFENCED|BOUND|FINALIZING,currentFenceEpoch}。FenceEpoch={unique_id,queue_id,ordered_position,condition,flags,completion_points,publication_scope}。重新Fence创建新epoch，不覆盖旧等待者的ticket。typed-v1 WaitSync在ENQUEUE锁存当前epoch；未Fence返回未满足依赖，不伪造success。CPU SyncWait锁存进入调用时epoch，timeout单位ns、0不阻塞，区分already signaled/condition satisfied/timeout/device failure。正式NVN何时锁存另列oracle门禁。

QueueFenceSync排序在pending queue当前位置；不是全局x_fence()。CommandBufferFenceSync在执行位置产生epoch实例，重放每次一个新实例。实际硬件支持不同scope时才映射条件；用submit尾完成替代早期condition仅在不产生额外依赖cycle并允许保守延迟的资格路径启用，并统计损失。

EventRef={PoolRef,logical_offset,32-bit width,alignment profile}。Initialize不修改value。CPU/GPU访问走统一alias和cache域；GetValue不得返回host缓存旧值。WRITE=0、ADD=1；按明确atomic协议实现ADD，不能CPU load/store与GPU RMW并发。EQUAL直接32位相等；typed-v1 GEQUAL_WRAP私有定义为 (uint32_t)(actual-target)<0x80000000，恰好半环差为false；该定义未获原机语义验证，不作为NVN已支持证据。location对应执行scope，TOP不等价完成callback；VERTEX_PIPE需后端明确stage支持；unknown flags拒绝。

QueryEpoch=(queue,logical_counter_type,reset_sequence)；Reset和Report是有序命令。Report capture当前累计值后写logical目标，不在录制时写回。typed-v1仅定义TIMESTAMP=0、SAMPLES_PASSED=1、TIMESTAMP_TOP=16，报告为两个little-endian u64: value,timestampTicks；tick单位来自profile，有证据的候选为19.2MHz但正式NVN资格须核对。内部GPU原始tick→guest tick使用宽乘除避免ns*12溢出。timestamp应在对应GPU位置采样，不能使用CPU completion clock。TOP和BOTTOM分别放置事件。

跨tile samples使用每tile同一逻辑epoch的部分和，binning阶段不双记；多个Report之间不隐式Reset；internal meta draw/query不能污染guest计数。输出alias视作GPU写依赖，CPU可见点需完成+cache维护。其余14种/特殊结构按真实枚举实现或拒绝，不返回伪0；报告不添加未经证明的availability word。

9. 阶段验收与门禁

V01：registry+ABI桥，ASan/UBSan canary测试覆盖0x80 texture/16byte view、commandBuffer+0x10写入不影响host指针、地址同值新代数。首版只host运行自编测试，不运行仓库游戏代码。

V02：双arena与事务Append。32/64/512byte小segment压力；独立control不足；回调补容量/无进展/更换userdata；callback内另一个recorder正常；同recorder递归Append被拒绝；End恰好使用末8bytes；连续Begin/End统计不清零错误。

V03：Call/Copy/patch。A含CallB、CopyA到C、改A不改C、改B依profile影响A/C；循环拒绝；同址句柄ABA；提交1后patch提交2，两批native视图互不污染；修改1块不重编其他块。

V04：descriptor/sync/query fake executor。录制bind后register新slot、submit可见新slot；未改变descriptor但资源publication变化仍发依赖；sync二次Fence不改旧等待epoch；event wrap边界和ADD冲突；多tile samples与线性reference一致；timestamp位置严格有序而非提交尾同值。

D2R准入清单：逐实际调用点枚举与flags、command存储直接写集、Copy可观察性/生命周期、sync锁存点、report输出ABI、SDK对象profile。清单尚未齐备就只标“CPU核心可开工/可测试”，不得标“原生D2R backend可开跑”。这避免以524行条目数替代真正语义闭合。

Adreno KGSL 首版内存合同 v0.2

本文件取代旧章节中与本文冲突的内存伪码；不替代 NVN 公共 ABI。目标是让第一个验证阶段 可写、可审、可做确定性故障注入。它不宣称 D2R 已可运行。首版不用 VBO，不承诺任意 userptr 导入、不承诺 sparse image；普通 BO 生命周期内稳定 GPUVA 即足够启动。GPU 控制和 cache packet 仍复用固定 Mesa 路径，不能把本 host 模型当成硬件证明。

1. 强制不变量

  1. 一个 guest 可观察 byte 的逻辑身份、实际 backing 身份、某版本 native 表示地址必须分离。Pool 销毁不立即使在途 backing 消失。
  2. 只有经 provenance 证明的 canonical backing 可以进入精确别名快路；unknown 不等于 no-alias。
  3. mapping snapshot 不可变，解析并 pin 是一个原子 owner transaction。
  4. 内容版本为区间上的事件集合，不跨 queue 用整数 max 定义新旧。同一区间无序写为竞争，不选择胜者。
  5. reader、writer、转换、CPU observer、未提交 plan 都持自己的 owner refs；完成一次 GPU 写不代表所有 refs 已退役。
  6. GPU 接受提交后不可 rollback；不确定是否接受也不能直接重试或回收。
  7. GPU 写入另一 layout 后，raw 可访问性只能在可证明的 read/write ownership 协议下开放；不以 snapshot diff 证明 byte 写集。
  8. 缓存命中只省元数据解析；当前 access reservation、内容版本和 cache domain 仍参与提交。

2. 初版数据形状

以下是内部 C++ 风格 schema，容器由 owner 线程管理；名称不是硬件结构。

struct ObjectKey { uint64_t id, generation; };
using PoolKey = ObjectKey;
using BackingKey = ObjectKey;
using QueueKey = ObjectKey; // generation 包含 context/device 重建边界
struct Range { uint64_t begin, size; }; // checked end; 半开区间，size=0 无 effect
struct LogicalSpan { PoolKey pool; Range bytes; };
struct CanonicalSpan { BackingKey backing; Range bytes; };

struct BackingRecord {
  BackingKey key;
  Provenance provenance; // OWNED_BO / VERIFIED_EXTERNAL_OBJECT / VERIFIED_HOST_ALIAS
  uint64_t byte_size;
  Vector<CpuAlias> cpu_aliases; // VA,length,object_offset,registration_generation
  Vector<NativeOwnerRef> owners;
  CachePolicy cache;
  GranulePolicy granules;
  RefCounts refs; // logical, prepared, cpu_lease, observer, accepted_gpu, quarantine
  Lifecycle lifecycle; // LIVE / DETACHED / QUARANTINED / RECLAIMABLE
};
struct MappingExtent {
  Range logical;
  CanonicalSpan canonical;
  uint64_t extent_generation;
};
struct MappingSnapshot {
  ObjectKey key; PoolKey pool;
  ImmutableVector<MappingExtent> extents;
  Vector<BackingRef> pins;
};
struct ResolvedSlice {
  CanonicalSpan canonical;
  NativeOwnerRef owner;
  uint64_t gpu_va, byte_size;
  RepresentationKey representation;
};
struct ResolvedBinding {
  MappingSnapshotRef mapping;
  Vector<ResolvedSlice> slices;
  RelocationProof address_proof;
};
struct ContentEvent {
  ObjectKey event; CanonicalSpan written;
  Producer producer; // sealed CPU publication or accepted queue point / reservation
  DependencySet predecessor_events;
};
struct AccessLedgerCell {
  CanonicalSpan span;
  EventSet current_authority;
  PointSet writer_frontier;
  PointSet reader_frontier;
  ReservationSet preparing;
  Vector<RepresentationVersion> representations;

2.1 身份注册

create_owned_backing 生成全局唯一 live ObjectKey。pool extent 显式引用这个 backing 及 offset。多个不同 Pool 只要引用同一 backing，所有 aliases 都归一个 ledger。外部 dma-buf/受控宿主对象必须持 owner 引用并验证对象 identity 和 offset 关系；同一个 fd 号不是 identity。未知 CPU 指针只证明虚拟区间重叠，不能证明不同 VA 不 alias。MVP 返回 UNQUALIFIED_ALIAS 并交还既有合格 provider，不能静默创建独立可写副本。

所有算术（logical end、backing offset、GPU VA+offset、alignment round-up、extent split）先 checked add/multiply。zero length 不建立 hazard，也不能借 zero-range 导出越界地址给硬件。地址/尺寸合法性必须早于 native encode。

3. 单 owner + 不可变 snapshot 的并发模型

MVP 用一条 memory-owner 执行队列线性化 registry/ledger，不先实现多锁细粒度版本。入口线程可查 immutable cache，但返回缓存命中后仍向 owner 提交 access recipe。不得在持 guest-visible lock 时同步等待一个可能回调 guest 的任务。owner 不执行 guest callback。

ResolveAndReserve(request) 一次 transaction：

  1. 验证 PoolKey/live、逻辑范围和 ABI consumption point。
  2. 取得覆盖整个范围的 extents，转换为 canonical slices；不允许洞被当零页。
  3. pin snapshot、backing、native owner，形成不可变 resolution。
  4. 按 canonical 边界切分 ledger，并计算读写/转换 dependency recipe。
  5. 以 reservation id 占位；该 reservation 引用已解析版本，其他 prepare 看得到。
  6. 成功返回 prepared token，失败原子撤销尚未接受的 reservation/ref，不影响已 accepted 工作。

Remap 也是 owner transaction：验证所有新 extents 和 pins，构建完整新 snapshot，发布一次替换；旧 snapshot 不改。MVP 不支持 NVN MapVirtual 就在 capability admission 拒绝，此算法仍用于 import owner/representation 改址和未来扩展。不能以 no-VBO 为理由跳过生命周期设计。

4. 区间依赖算法

访问集合必须先 canonicalize，再按端点 split。范围之外 cell 不变。Access 包含 semantic effect、preservation closure、domain 和 read/write/RMW，不能用 view 身份隔离 hazard。

  • Read：从目标版本 writer frontier 取 producer 依赖；登记本访问为 reader。读不同 layout 时转换本身先作为 reader，再为 destination representation 建 write reservation。
  • Write：确认保留未覆盖内容所需 reads。要求 guest 顺序证明覆盖旧 writer 和 readers；生成对应 RAW/WAR/WAW 和 cache transition。完成后替换被实际覆盖区间的 authority，不影响其他区间。
  • RMW：同时读与写，按该硬件原子粒度记录；多个 native 副本不能共同实现同一原子位置。
  • 无证明的冲突：输出 UNORDERED_ACCESS 诊断/unsupported，不替 guest 发明全局顺序。实现内部的 copy/retirement 依赖可以增加，但不得错误消除 guest 对外 wait/signal。
  • Read frontier 可在同 queue 且有确定支配关系时压缩为最晚点；跨 queue 保留集合。任意 publication scalar 都只是集合 registry key。
  • GPU 完成只消去 execution wait；domain 可见性需独立检查，不以 “timeline 完成”省掉 texture invalidate 或 CPU cache maintenance。

prepare 预分配 submission journal 和 pending effects。submit acceptance 使 reservation 变成 accepted queue point；尚未接受部分的 abort 只撤销它自己。转换 key 至少为 canonical span、exact_source_events、目标 layout/format/算法版本、preservation coverage。完成回调安装旧 source version 的 representation 时先比当前 authority，不能覆盖已更新 authority。

5. 无 VBO 的连续范围与 copy

普通 KGSL BO 的 gpu_base 在 owner 寿命内稳定。一个硬件 buffer descriptor 要求的连续区间必须满足其中一种：

A. 一个已有 owner 完整覆盖，直接返回 offset GPUVA。 B. 资格化 import 可覆盖整个范围且共享相同 canonical backing，新增 owner 但不新增独立内容权威。 C. 形成单次消费 writable-alias connected component 的 union BO；所有访问均可重定位到同一个 union 地址体系，conversion 保留其版本语义；copy-in/out 作为普通 ledger 操作。 D. 无法证明 A/B/C，返回 UNREPRESENTABLE_ALIAS，不能为每个 view 单独 copy。

component 包含此次 shader 可达所有 read/write/atomic views，未知动态指针范围按其已证明上界保守加入。union 超预算、有洞且不能合法初始化、跨对象原子或指针逃逸不支持就拒绝。只读 isolated copy 必须资格化为不参与 concurrent writes 的版本快照；不能普遍把执行期读取变成提交前读取。

6. CPU ownership 和 granularity

6.1 MVP：显式 lease，不先开发信号故障引擎

BeginCpuRead(range) → ResolveAndReserve → 等所需 producer（不能持 owner 锁等待）→ raw materialize → cache visibility → return lease/可访问指针。

BeginCpuWrite(range, coverageProof) → compute preservation closure → 同步已有合法 readers/writers → materialize 未覆盖 bytes → 获取 ownership → return lease。只有 proven full overwrite 才可跳过相应保存；普通页 fault 不是 full overwrite 证明。

EndCpuWrite(lease, exact_or_conservative_written_range) → release/acquire CPU publication boundary → cache clean 按正确 granule → 生成 CPU ContentEvent → release lease。CPU publication 的 timeline=0 不表示无 happens-before，仍带 writer epoch 和事件身份。

缓存非 coherent 时，以 cacheline 扩张 ownership，所有 overlapping native writes 必须排除。coherent 只省 CPU cache 维护，不准无序原子外读写。保护页、cacheline、layout-preservation unit 三种粒度单独保存。

PreservationClosure 算法：从 effect range 开始，求其映射到所有需保留 representation 的 units；把这些 unit 映回 canonical bytes 后 union，再对 alias CPU 页/缓存粒度取闭包，直到不再增长。若越过已知 allocation ownership、超过预算或格式不可逆，返回明确 unsupported/materialization policy，不推断 padding 可丢弃。此 closure 只决定要 preserve/独占的范围，不把它变成 semantic written range。

6.2 后续 lazy observer gate

只有满足以下条件才启用：全部 CPU alias VA 受控；保护页不含控制面对象；预分配且预触 fault slots/altstack；平台 signal transport 与 park/unpark 已单独证明；owner 对该资源的工作不会等待 faulting thread 提供的 guest event；CPU 多线程写入在 guest 合法发布边界有 seal。handler 只提交固定 token 和 park，绝不执行驱动、分配、复杂查表或拿 owner mutex。若不支持本平台可靠 transport，就采用显式 CPU instrumentation/已有合格 observer，而不是写一个“应该 async-safe”的临时 handler。

writer epoch：CLOSED→OPEN→SEALING→SEALED。SEALING 只在 guest 已停止该范围合法 writers 的边界启动；等已登记 leases 归零，所有 alias 改为适当保护，完成平台要求的可见性屏障后采集 dirty set，发布 SEALED。mprotect 不提供任意 guest store 的精确计数，不能假设单靠页重保护就完成 seal。新 writer 属下一 epoch；若 boundary 不能排除不经 lease 的并发 stores，该模式未资格。

7. 命令消费快照

typed 模式只复制规范要求的 record-value 状态，资源数据仍按执行期读取。raw-compatible 模式要求可识别 command ABI、storage owner generation 和 sealed writer epoch：seal→复制命令 bytes→解码→校验合法字段→建立资源 bindings。重用 IR key 为 storage generation、sealed bytes digest/patch generation、ABI、被引用对象 capture generations。已完成快照后改 raw bytes 不回写在途 snapshot，但这只适用于已证明允许 submit 边界捕获的 profile；执行期可修改描述符另设协议，不能混同。

未 seal 的命令页不得开始解码；运行时消费者语义未核验就拒绝 raw-compatible，而不是用二次 version read 假装原子快照。既有 command bytes 与 descriptor source raw bytes 的观察器版本必须独立于图像 content version。

enum Acceptance { NONE, PREFIX, ALL, UNKNOWN };

MVP 一 transaction 最多一个 GPU_COMMAND，所有 journal slots/refs/sync bookkeeping 预分配。状态 PREPARED→SUBMITTING→ACCEPTED→COMPLETED；另有 NOT_ACCEPTED、OUTCOME_UNKNOWN、DEVICE_LOST_QUARANTINED。禁止从 ACCEPTED 回 PREPARED。

  • NONE：每个 chunk 都有未被接受的证据（未调用，或已验证 kernel error 合同证明未接受）。只说 ioctl 返回非零不足以覆盖所有错误路径。
  • PREFIX：accepted 恰好是连续成功前缀，其余全部可证未接受；允许取消剩余部分，不允许重发前缀。
  • ALL：全部工作接受，不承诺已经完成/CPU visible。
  • UNKNOWN：至少一个已尝试 chunk 的接受性不能证明；仍保留已确定 accepted 的前缀，first_unknown 不得计入 proven_unsubmitted。不自动 retry。

GPU_COMMAND 成功后立即把 timestamp 与预分配 journal slot 原子提交。fence export 失败只记录 export_error，仍可在相同 context 上按真实 timestamp 等待；若无可用完成机制，quarantine。outcome unknown 的所有可能被 GPU 使用对象保持 quarantine，等待已验证 context teardown 保证再无访问。通知上层 device lost 不等于可 free。针对多个 backend chunks，journal 每次 ioctl 后递增，禁止在循环末尾一次性写总结果。

QueuePoint 的 host_serial 为 host registry 的单调序，不等于 KGSL uint32 timestamp。timestamp wrap、context reset、empty wait-only submit 遵循固定 driver adapter；不在 core 中比较 uint32 大小。empty submission 的 completion 是真实前序+wait 集合，不能使用不推进硬件 timeline 的伪点。

Reclaim(owner) 充要条件：logical refs=0，prepared refs=0，CPU leases=0，observer callbacks=0，所有 accepted GPU refs 已可证明终结，quarantine=0；随后先解除可触达 mapping/observer registration，再释放 native owner，最后回收 registry/tombstone。旧 generation 回调只能失败返回，绝不解析新对象。公开 pool finalize 可先 detach，不能强迫马上 free。

硬件 gate（与 host验证阶段 独立）：ordinary BO CPU↔GPU checksum；cache granule policy；真实 context completion/wrap 处理；单 ioctl failure/quarantine；acquire/present 外部生命周期。custom import、VBO、未知 userptr、raw command late patch、lazy observer、compressed raw roundtrip、跨 queue timeline 外部互操作分别单独资格化。资格结果必须记录 device/driver/kernel/flags 精确组合；不得用一次 coherent buffer 成功替代整个组合验证。

9.1 Reservation 的取消与真正发布（补充强制条款）

prepare 只能增加 tentative reservation，绝不提前覆盖 committed authority，也不能创建可送入 kernel 的虚构 queue timestamp。若 B prepare 依赖尚未 accepted 的 A，B 持 A 的 reservation ID，等待 A acceptance 后解析为真实 point；A 若取消，B 必须重新规划或取消，不把“未提交 A”当可等待 point。多 chunk prefix commit 只为 accepted chunks 安装新 authority/reader frontier；proven-unsubmitted suffix 回滚自己的 tentative effects，unknown chunks 隔离相关区间并停止新消费者，不能声称数据仍为提交前版本。单 queue 也需 stage/cache RAW/WAR/WAW：host FIFO 提交顺序不自动等于所有流水线访问完成顺序，不能省掉对应硬件事件/屏障。

9.2 同步存储与并发原子不是普通 data frontier

AccessRecipe 必须额外包含 AccessClass：DATA_READ、DATA_WRITE、DATA_RMW、SYNC_POLL、SYNC_SIGNAL、ATOMIC_RMW。第 4 节普通 RAW/WAR/WAW 仅适用于普通数据/转换访问；不能用于推导一个 signal 等待正在等待它的 poll 退休。

EventAccess 记录 canonical word range、event generation、comparison predicate、signal value、release/acquire scope、native cache protocol 和 queue position。SYNC_POLL 对信号值的观察不加入该 word 的普通 read frontier；SYNC_SIGNAL 的 signal write 不等待这个 poll，真实 completion 由原事件协议产生。前后普通资源的 release/acquire 关系仍由 event 建边。只特判准确 event word，绝不把所在页或整个 backing 从数据依赖中删除。把同一个 word 当普通数据读写的调用需要已证实 ABI 语义，不自动获得 signal 例外。

ATOMIC_RMW 可存在合法无总序的并发生产者：保存 atomic access group 及最终 observer 所需所有 points，不强行确定每个中间返回值顺序。准入条件是同一 canonical/native backing、相同可互操作的硬件原子 scope、alignment/width、内存序，并且没有未同步混入的非原子覆盖；native/raw 转换期间不允许两副本各做 atomic。首版不支持的跨 CPU/GPU atomic 类型明确拒绝，不能把 CPU coherent 当成原子互操作资格。

CPU fault/materialization 不得 park 在将由 faulting CPU 负责 signal 的 event store 之前。同步 word 必须在注册时确定可直接访问/正确缓存的表示；未知 stale-raw event word 无法安全 lazy materialize 时提前拒绝该模式。

  • 0x00 u32 abi_version=1；0x04 u32 flags（未知位拒绝）；0x08 texture_count；0x0c sampler_count。
  • 0x10 storage_image_count；0x14..0x3f 保留全零。
  • 0x40 + 0x40*s：u32 ubo_count @+0；u32 ssbo_count @+4；u32 stage_flags @+8；u32 draw_id @+12；i32 base_vertex @+16；u32 base_instance @+20；u32 dispatch_base[3] @+24；余下28B保留全零。

Root 不含 MapEpoch/PublicationEpoch 等 CPU bookkeeping，也不假装能替代 ir3 的 driver params。base vertex/instance、drawID、workgroup 参数仍由对应 NIR system value 和 Turnip driver constant path 驱动；root 中同名值供 guest ABI 显式读取时使用，测试两条路径一致。没有使用字段不发 shader load。root 通过 bank3 index0 的 UBO load 访问，因此不会抢占手写 constfile 区间。ir3 仍可以合法提升/预取，依靠其 allocator 管理，禁止自己规定 c-register 编号。

2.3 大 pool 和索引边界

MAX_SET_SIZE=1GiB 是 Turnip 为 CP_LOAD_STATE6 28-bit DWORD offset 选的实现上限，源码只保守说 hardware 至少支持 2^16 descriptors，不是已证明 NVN 全部 20-bit 索引范围。ir3 动态 texture/sampler source 是 vec2 32-bit（ir3_compiler_nir.c:1835-1977），常量 >=256 转 S2EN，不应以短 immediate 位宽判断硬件上限。

初始能力表 qualified_texture_slots 独立于 guest_pool_capacity。先要求实际访问集合不超过已验证 native range；若 pool 容量更大但可证明静态仅访问小集合，可用显式 dense remap variant，不能仅凭上一帧没访问当证明。运行期任意索引需要完整范围编码/边界检查和最大索引 GPU 用例通过后才开放。full20bit 表需 (2^20+1)*64 bytes/bank，bank0+2 即约128MiB；不是每 draw 创建，不预先假设移动设备可承受。替代方案 shader 查 remap table 加依赖 load 是独立 ABI_2，不能无声改变 ABI_1。安全空 slot 不等于对所有 guest 越界定义了返回零：合法语义不能满足时在 native eligibility 阶段失败。

3. NIR、linkage、机器码之间的具体接线

首版刻意保留 Mesa 内部固定 tu_pipeline_layout 元数据形状，避免第一周同时重写 NIR lowering。它不是 VkDescriptorSet/VkPipelineLayout handle，也不创建用户可见 Vulkan descriptor 对象。新增 schema 构造器只填 num_sets/set[].layout/binding[]/size/push_constant_size/dynamic_offset 等实际被 compiler 读取的字段；必须静态列出字段读取并补全 required state。未来去 Vulkan 类型是单独 refactor，不是速度目标。

新增接口与职责：

  1. nvnn_build_resource_schema(DeviceCaps, Abi1Schema*)：上节四 banks，typed binding offsets，layout hash，校验 caps.max_sets>=4、descriptor size组合和 range。
  2. nvnn_guest_to_nir(GuestProgramSnapshot, GuestResourceManifest, Abi1Schema, nir_shader*[])：输出常规 shader inputs/outputs、UBO/SSBO resource index/load descriptor 链、image/sampler deref。sampled texture set0 binding0、sampler set1 binding0、storage image set2 binding0；root set3 binding0；每stage buffer按表。guest index解码、bounds和+1在此。不得残留 guest CPU pointer 作为 GPU pointer。
  3. 每stage 跑 tu_lower_nir（其中 :3589 把UBO/SSBO显式IO降为 nir_address_format_vec2_index_32bit_offset），再 tu_link_shaders，然后 tu_shader_create。真实顺序见 tu_shader.cc:3950-3965。NIR 验证放在 guest adapter 后、link 后、finalize 后；不允许在后端机器码生成后补资源 ABI。
  4. tu_shader_create:3655 内部：tu_lower_io:1462（包括常量分配与descriptor conversion）→gather_info→ir3_finalize_nir→tu_nir_lower_ssbo_descriptor:3705。必须保留该最后 pass，因 vectorization 才决定 SSBO bit size。shader->active_desc_sets、conststate、driverparams、安全const variant都由这条路径产生。
  5. nvnn_link_native_program(CompiledStages, FixedFunctionKey, NativeProgram*) 从 tu_pipeline.cc program state 构造抽出配置：tu6_emit_program_config:1348/2398 必须在依赖 config 的 constants 之前；VFD destinations、VS/FS varying linkage、FS inputs/outputs、SP state不能只凭 binary address猜。tu_shader.cc:2524,2595,2796,2883,3050 是具体 emitter anchors。

tu_lower_io 的 dynamic descriptor stride 要是二次幂；ABI 的1/2满足。动态索引不得盲加 ACCESS_CAN_SPECULATE；保留 can_speculate_descriptor_load 的条件、nonuniform 标记和 guest binding有效性。lane-varying texture/sampler 索引必须有测试，不能把动态误当 uniform。初版为每个 Program+ABI 输出 manifest JSON，列出所有资源 kind、stage、binding、bounds、读写/atomic、副作用、stageIO；manifest 不完整就不启用原生路径。

4. 状态缓存与 native block 所有权

所有 key 都包含 DeviceCaps fingerprint（精确gpu/chiprevision、compiler options/workarounds）、Mesa commit、ABI version。以下是字段契约，不是仅存 dirty mask：

  • ProgramKey：guest shader/control bytes hash + semantic adapter version + specialization bytes + stageIO linkage + resource schema hash + subgroup policy + float/precision policy + required robustness + shader relevant attachment formats/sample/read-only feedback。没有把每帧内容 epoch放进 key。
  • ViewKey：ResourceId generation + canonical backing span identity + MapEpoch + format/aspect/swizzle + dimension/mip/layer范围 + stride/layout/UBWC模式 + GPUVA + access kind。content改变不必重编码；重映射必重编码。
  • SamplerKey：全部采样/比较/LOD/anisotropy/border bits + border table generation + devicecaps。border table slot生命期随sampler而非frame。
  • RootTableKey：Program ABI + pool identity/generation + descriptor slot versions + 每 buffer view/address/range + root bytes hash；不能只比较 pool pointer或draw的句柄值。PublicationEpoch 影响依赖，不机械改变相同descriptor bytes的key。
  • ProgramStateKey：linked variant IDs + VFD格式/stride/instancing + shader output mapping + sample shading和rasterization影响编译配置。
  • RenderStateKey：attachment native views/physical generations + render area/layers/sample + blend/depth/stencil/rasterizer/viewport/scissor + sysmem/GMEM plan version + LRZ/CCU mode。不同组可拆 key，但总覆盖集合不能省。
  • HazardState：按canonical backing byte/subresource范围，最近writer/readers的queue completion与访问domain、materialized representation；不与 descriptor cache混合。

NativeProgram/code、NativeDescriptor、RootTable、NativeStateIB、DrawIB各保存 referenced BO集合、relocation generations和所有 queue 的 RetireSet。已交给 GPU 的 bytes immutable；同一值新版本可以共享，同一地址新内容不能“顺手覆写”。command storage 的合法 guest patch 在语义消费点重新解析/capture，选择新的native block；禁止用 immutable native cache否定 guest command可写性。所有 IB 引用的descriptor/BO 纳入 submission residency/lifetime，不能只上报直接 command BO。

NvnnHwState { context_generation; gfx_valid_mask; cs_valid_mask; cache_domains; } 是 context内实际寄存器状态，和逻辑 NVN state 分离。每个 emitter 返回 WriteSet { gfx_groups, cs_groups, cache_domains, query_state, lrz_state, render_mode }。正常draw、compute、clear(2D/3D)、retile、resolve、querycopy、event、prologue/epilogue、恢复context都是 writers。首版任何 meta kernel/3D clear后将全部 GFX/CS group invalid，再按真实 key 重发；以后逐writer收窄。未知 packet writer=all invalid。缓存IB本身只避免再生成 bytes，不表示 GPU 当前已装载该状态。

5. 顺序、cache 与真实提交完成

NativeAccess 包含 backing span、读/写/atomic、pipeline stage、cache domain、representation。域至少区分 CPU、CP/sysmem、UCHE、CCU color/depth、CCHE、bindless descriptor cache、GMEM/blit cache。按别名span算 RAW/WAR/WAW，不以 texture对象ID替代。相同GPUVA不同view的 storage write→texture sample仍须dependency。

首版采用完整 conservative dependency emission，不从“同一submit”推断缓存一致。上游 tu_cmd_buffer.cc:5790-5880 明确：UCHE/CCU clean与目的invalidate关联；descriptor destination另触发 bindless invalidate；CCHE有多个不一致副本不可简单删invalidate。tu_emit_cache_flush:393 还有 SP_GFX/CS_BINDLESS_INVALIDATE，不能只更新 base忽略 descriptor cache。CPU改 descriptor时先按映射cache policy做host publication，再在首次GPU消费发descriptor invalidate；CPU-GPU coherent不自动使GPU所有cache互相一致。

新增 nvnn_plan_dependency(accesses, HazardState, ExecutionPoint) 输出 availability(clean)、execution wait、visibility(invalidate)、GMEM materialize，以及producer completion set。不能将这四项合并成一个 bool barrier。A7 BV/BR开启后目的vertex阶段wait需要双方参与（tu_event.cc:152-181）；首版禁并发避免漏半边，不把缺失当 hardware不能做。

保留 tu_EndCommandBuffer:5448 对pending+CCU尾flush的语义，最后signal/completion必须在这些写可见之后。kernel完成/UCHE行为不是CCU写回保证。以后只在native batch知道最后真实IB及外部消费者时合并中间clean，不是“删所有Vulkan尾flush”。NVN EndRecording不强制GPU提交；提交时点和nativeIB边界分离。

KGSL context timestamp映射单调内部u64 serial；32-bit wrap用固定窗口内模比较，禁止跨>=2^31未完成跨度。跨context/外部sync用真实dependency，退休取全部完成集合。empty/wait-only batch不伪造推进：走KGSL已实现的特殊sync处理或发合法最小GPU工作并验证有completion。用户返回的 NVN fence/query时间不是cpu wallclock，更不是内部 serial。

6. GMEM 与 once-only 的增量契约

首版每个 Query/Event/Sync publication、compute、copy、alias observer、非framebuffer barrier 结束 RenderEpoch。在有序一次性主CS执行，再开启后续epoch。这是合法的保守实现，可牺牲部分tiling，不改观察点。不能把所有event统一移到epilogue，例 Signal(A); Wait(A); Draw 会变成等尚未执行的 signal。

GMEM admission第二阶段要求：attachment集合/format/sample/extent兼容且可装入；没有任意texture反馈；跨tile读取无；没有未实现replay side effect；有效load/store/clear；外部observer和alias边界清楚；binning shader const布局与render variant相容；VSC容量溢出有上游fallback/overflow处理。过关前不启 concurrent binning。

每条 IR operation必须枚举执行域 ONCE_PRE / BINNING_ONLY / TILE_REPLAY / ONCE_POST / EPOCH_BOUNDARY，不可默认全部复制进draw_cs。VS/GS storage/atomic/XFB是不同于普通FS color store的副作用。初版 GMEM白名单只接受无非attachment shader write/atomic的VS+FS；其他shader保持sysmem，后续靠经过验证的binning variant/conditional exec处理，不能简单“有binning所以只执行一次”。

查询处理：

  • Timestamp：按guest stage规范在原执行位置采真实GPUcounter，结果写与availability独立。tu_query_pool.cc:2109 在Vulkanrenderpass里每tile重写取最后值，是 Vulkan特定可接受策略，不直接视为NVN时间点oracle。初版epoch split后采一次；counter位宽、频率、wrap与guest tick换算用设备与guestABI证据，禁止硬编码一个GPU频率。
  • Occlusion：begin/end计数差值覆盖原draw区间；跨epoch保持logical query active并累加native segment，不重复begin导致丢前段。多tile可累加per-tile，结果/availability直到全部片段完成。
  • Primitive generated/XFB：上游 tu_query_pool.cc:1425 明确即使HW binning，tile也会再次计数，使用 SYSMEM|BINNING 条件执行。首版sysmem；GMEM时移植完整条件与begin/end accumulator，不能简单除tilecount（边界tile并不均匀）。
  • query reset/reuse按query generation；GPU query destination与CPU读/间接draw别名时进入一般hazard。result可见后availability才为真，复制查询结果到guest memory必须正确宽度/stride/未就绪语义。
  • Event/Sync：实现value/mask/比较/更新模式来自guest ABI，不直接假设 Vulkan boolean event。独立 recording contract确定细节；未确定的模式不得落到固定 CP_WAIT_REG_MEM == 1。每个signal记发布的scope，wait应用自己的consumer scope，跨queueforward wait不得把CPU提交线程阻死。

7. 开工测试与验收，不宣称已执行

8. Hardware限制与实现限制分类

A6五bank/A7八bank、descriptor索引编码和GPU缓存域是hardware机制。Tessellation sysmem、部分query需要binning、feedback禁GMEM是该Mesa硬件路径的实际实现约束，不证明NVN/API禁止。首版32个buffer/不支持GS/禁concurrentbinning是工程范围。Vulkan pipeline/layout重复构造可以删；合法依赖、tile materialization、guest布局转换、shader语义差异不能靠去掉API消失。UBO root与固定私有layout的方案用Mesa内部编译基础设施，不是重新套回逐draw Vulkan对象翻译。

补充：事件轮询不属于普通数据 WAR frontier

对 event word 使用 SYNC_POLL / ATOMIC_SIGNAL 独立访问类别。若普通 hazard planner 把 SignalEvent 写排在未完成 WaitEvent 读之后，会自造WAR死锁；但也不能把整页event backing排除普通hazard。协议只作用于精确word，signal携带发布数据scope，wait携带消费scope。对CP_WAIT阻塞的队列，同队列排在其后且未能执行的signal不是可推进producer；必须存在可运行的CPU/其他context producer，或由调度器在不改变guest顺序前提下形成合法依赖，否则拒绝该调度。测试包括wait先提交、外部signal后提交、同页非event RAW，以及同CP forward-signal死锁检测。

PanVK 对第三轮修订的继承范围

本次“开工”收敛到已选的Adreno/KGSL。PanVK独立二版仍是候选设计，没有执行新Mali硬件资格或承诺同时实现。

未来PanVK必须继承的语义修正：

  • canonical backing与alias provenance，而非PoolId/VA/BO编号即物理身份。
  • reader/writer frontier、tentative reservation及内容版本，普通WAR不套在event polling word上。
  • 同一shader中的可写别名不能被独立shadow拆散。
  • submission接受性、完成性、导出失败和device lost隔离分开；CSF多queue/group应按自己的实际接受原子性记录receipt图，不机械复制KGSL前缀模型。
  • SDK对象profile、可观察command预算、Copy/Call与FenceEpoch消费边界独立核实。
  • native窗口buffer/acquire/release与descriptor/IB寿命分别管理。

不能继承的Adreno细节：4-bank ABI、64B索引单位及SSBO双槽规则、PM4/CP_SET_DRAW_STATE、KGSL uint32 context timestamp、tu_device冷启动和CCU/UCHE协议。Mali必须保留Panthor CSF、kbase CSF和JM各自的实现路径。

因此本版并未把PanVK文档宣称为“也已可直接开工”。启动Mali时，要在已可用的实际kernel/WSI平台上重新完成对应构建闭包、native资源ABI和提交失败语义审查。
