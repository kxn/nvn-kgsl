# Device API version follow-up: an explicit partial-ABI identity

This is read-only research, not a build or device test. No tracked edits, ADB, git, CPU simulation, game patch or Vulkan implementation was used. This follow-up resolves the policy left open in `device-bootstrap-next.md`: a measured original NVIDIA runtime version remains unknown, but that does not prevent this independently implemented backend declaring a stable, explicitly partial compatibility identity.

## Recommendation

Adopt the immutable project profile **`nn-nvn-partial-abi53.105-v1`**, with `DeviceGetInteger(API_MAJOR_VERSION=0)` returning **53**, and `API_MINOR_VERSION=1` returning **105** for an initialized native device. These are **project-declared ABI-dialect values**, chosen because the pinned reconstructed header documents that type/enum basis. They are not discovered NVIDIA driver/firmware versions and do not certify all features or functions of NVN 53.105. This choice is an implementation policy supported by source provenance and the actual consumer analysis below, not a claim that a public document prescribes this pair for this new backend.

The contract is concrete rather than a generic success stub: the backend implements the declared typed C calling conventions and object/handle representations for its supported subset, and returns the immutable identity of that dialect when asked for API version. Unsupported functions/configurations still stop independently; the version never synthesizes capabilities. The named profile, numeric values, `partial=true`, `strict_unsupported=true`, pinned header hash and API-source hashes must appear together in its build/qualification metadata. Do not label the pair `measured_nvidia_api_version`. Emit its declared identity once in native bootstrap diagnostics so a guest printing only numbers cannot become an unqualified hardware claim in the evidence report.

Place the constants/profile definition in the native implementation's normal interface or metadata, not a game-address exception or adapter rewrite. Core `DeviceGetInteger` should validate device/output pointer as it already does, write exactly one 32-bit int for properties 0 and 1, and otherwise retain its existing explicit switch/unsupported diagnostic. The same initialized device gets the same pair irrespective of caller address, Release/Debug configuration, query order or builder flags. The pair is independent of Adreno chip, Android/kernel, Mesa, shader translator and GLSLC GPU-code versions.

Do not return 53.311: its only inspected local source explicitly calls it unverified. Do not return 0.0 to express partiality: no public NVN rule for that meaning was established. Partiality belongs in the named project profile and fail-closed capabilities, not an invented meaning for the numeric API version. Do not choose a larger minor to defeat a consumer comparison. If a different verified consumer later has a meaningful incompatible branch, investigate the underlying required ABI/feature and version the project profile deliberately.

## Actual original D2R consumer: the two outputs are dead in the initialization function

Raw original main SHA256: `6843ab6909f96e1558b4b73b0fa807f3873409120cf3e1ef8a86dbebb275ee27`; raw path and NSO hash are in JSON. Existing `dm/tools/sdis.py --fn 0x173cbe8` resolves its eh-frame-bounded function to **[main+0x173c5e0, main+0x173dc18)**. Existing Capstone decoded only this 5688-byte function (1422 ARM64 instructions). This is static assembly/CFG inspection, not instruction execution or an interpreter.

* Prologue at 0x173c5e0 reserves 0xe0 bytes; 0x173c5fc sets fp=sp+0xd0. Neither base changes after the queries until the normal epilogue.
* Major property 0: output address at 0x173cbdc is fp-0x58, hence **sp+0x78**; actual indirect call 0x173cbe8.
* Minor property 1: output address at 0x173cbf0 is **sp+0x34**; actual indirect call 0x173cbfc.
* The minor location has no later direct load, pointer formation or outward store of its value in this function. It is abandoned at function return. The later builder temporary begins sp+0x38, not sp+0x34.
* The major location likewise has no later direct value load. At 0x173d6f8 a full eight-byte store replaces sp+0x78 with the current return value of another API. Subsequent code uses that location as a single command-handle temporary: 0x173d700 forms its address, and a loop backedge can reach 0x173d318/31c/320, which selects and loads from that temporary for vector insertion. This later read must not be mistaken for consuming the API major version.
* As an additional offline check, a direct-branch CFG from immediately after both queries (0x173cc00), treating typed calls as returning and removing the overwrite instruction at 0x173d6f8, cannot reach either that pointer formation at 0x173d318 or read at 0x173d320. No non-call indirect branch exists in the bounded function. Normal return can be reached without the overwrite through other paths, but those paths do not read either version output.

Conclusion: **no comparison, format/log operation, branch decision, persisted object field or forwarded argument consuming either original version value was found in this actual initialization function.** The values are written and discarded/replaced. This strengthens the earlier short-interval observation to the complete eh-frame-bounded function. It establishes no hidden required minor, and does not establish that arbitrary unrelated SDK applications never compare API versions. Ordinary declared call-boundary memory semantics are assumed: a driver may write its declared output during the call, but must not retain a pointer to a caller's stack-local version integer for asynchronous use.

The next actual calls are window origin mode 1 at main+0x173cc10, depth mode 1 at main+0x173cc24 and memory-pool setup. Reporting the profile identity would permit the original unmodified function to proceed to those real semantics; it does not bypass a verified version-dependent game branch.

## SDK/public ABI evidence and limits

The pinned `nvn-native/third_party/nvn/nvn.h:23-26` identifies a partial type/enum reconstruction with 53.105 as its basis. Lines 232-233 separately define the API major/minor query selectors; line 1127 declares the real `void (const NVNdevice*, NVNdeviceInfo, int*)` PFN. The values are written through the typed third argument; the function has no success return scalar to fabricate. The opaque object sizes, 64-bit handles and enum widths in this same pinned header are already the project's external ABI basis.

Public primary reconstructed sources inspected:

* [Reconstructed NVN header](https://code.botw.link/uking/uking/lib/NintendoSDK/include/nvn/nvn.h.html): establishes type/enum basis and query meanings; not runtime measurement.
* [Inline NVN forwarding](https://code.botw.link/uking/uking/lib/NintendoSDK/include/nvn/nvn_FuncPtrInline.h.html): lines 34-35 forward the typed query to the loaded driver pointer without supplying their own numeric version.
* [Reconstructed Horizon gfx device initialization](https://code.botw.link/uking/uking/lib/NintendoSDK/src/NintendoSDK/gfx/detail/gfx_Device-api.nvn.8-os.horizon.cpp.html): initializes the device, reloads procedures and queries a separate device-feature facility. This reconstruction supplies no numeric runtime API-version result and is not proof for this game's SDK binary.
* [Separate feature declarations](https://code.botw.link/uking/uking/lib/NintendoSDK/src/NintendoSDK/gfx/detail/gfx_NvnHelper.h.html): describes feature queries independently of API identity. This supports keeping identity and supported-feature accounting separate; it does not validate any particular capability of the new backend.

Local original SDK symbol metadata identifies exported `nvnBootstrapLoader` (0x4a3120, size0x58) and `nvnBootstrapLoaderInternal` (0x4a3180, size0xc). Previous bounded inspection of these hash-verified original SDK functions shows delegation through a loaded/cached external driver pointer, not a built-in numeric API version response. The symbol metadata search found no exported `nn::gfx` Initialize, NVN GetInteger or version implementation to justify extending the binary investigation. No whole-driver reverse engineering or claim about all stripped SDK consumers is made. A full original NVIDIA version response remains **unknown**, and is not needed to name this project's own partial dialect profile.

## Failures remain meaningful under the proposed profile

This is deliberately a partial facade: lookup names absent from core still yield NULL; the typed D2R adapter still exits on unsupported lookup, known-call errors and unknown ABI calls. A positive API major/minor identity must not clear a prior sticky diagnostic or register fabricated function implementations. The 46 currently undeclared names remain UNKNOWN typed boundaries. Capabilities and limits continue to require their own implemented semantics and evidence; unknown property values stay ENOTSUP with the output sentinel unchanged, rather than defaulting to zero. For a genuinely implemented feature-query contract, a proven unsupported boolean can eventually be 0, but not by automatically converting every unsupported query into success.

Thus API identity is not a promise of all API operations succeeding. This limitation is explicit and machine-readable in the named project profile, and observed calls remain strict. This is suitable for the current incremental porting/qualification scope; it must not be presented as a conformant full NVN driver.

## Executable validation boundary for the owner

Proposed, not performed here:

1. Direct typed tests: each query writes exactly one int (adjacent guards unchanged), repeated/reversed-order queries return 53/105, null output and non-device object reject, unrelated properties retain ENOTSUP and their sentinel. Confirm an existing sticky diagnostic is never cleared by the adapter or identity query.
2. Metadata test: generated native/bundle record includes the exact profile/pair/header hash, `partial=true`, `strict_unsupported=true`; it does not label the pair as measured NVIDIA or GLSLC code version. A supported API subset expansion changes implementation/source fingerprints; incompatible ABI dialect changes require a new profile instead of a per-game-number override.
3. Preserve adapter negative tests for absent function, UNKNOWN ABI and unsupported argument after adding the two successful properties. Version success must not cause unknown entry points to become permissive stubs.
4. Rebuild through the existing recorded original-input pipeline. Run the unmodified real modules through the existing host. Typed logs should show exact flags, Initialize result, GetInteger property/output, and next real call/module+offset. A run stopping at origin/depth/pool contracts is honest progress to the next semantic boundary, not rendering success.
5. Record actual SDK/ctors/nnMain execution separately from host-only scalar tests and existing original-shader GPU qualifications. No original game frame is claimed by this research or by returning the profile identity.

## Suggested manifest and lifecycle checks

Use a versioned object such as `nvn_compatibility: {schema:1, profile:"nn-nvn-partial-abi53.105-v1", reported_api:{major:53,minor:105}, identity_kind:"project_declared_partial_abi", partial:true, strict_unsupported:true, original_driver_version_measured:false, abi_header_sha256:"...", core_source_sha256:"...", entries_source_sha256:"...", typed_names_sha256:"...", unsupported_properties:"ENOTSUP_output_unchanged", unknown_abi_names:46}`. Pin the actual computed count/hash rather than relying on this prose count after metadata regeneration. Also retain actual target-chip qualification separately; this ABI object must not transform A735 evidence into A650 capability evidence. Include the same profile in host executable build records; a manifest-only claim without compiled constants matching it is insufficient.

Test the version query at the following lifecycle boundaries: before Initialize, wrong object kind, null device, after failed Initialize (no valid device created), after successful Initialize, after successful Finalize, and while a Finalize attempt has failed EBUSY (the still-live device should remain queryable). Reinitializing the same caller storage should acquire a fresh live object and report the same immutable pair. Builder SetDefaults or SetFlags after creating a device must not alter the device's API identity. Null output is EINVAL and must not dereference; invalid device is EINVAL and must not write the output. Successful major/minor each writes one int with unchanged adjacent guards. Unknown property preserves a sentinel and ENOTSUP. Test each failure independently so a previous sticky error cannot be mistaken for the current error; explicit diagnostic reset is allowed in a qualification harness between isolated cases, never as an automatic adapter behavior.

Error precedence for a null device combined with null output need not be over-specified beyond EINVAL/no writes; do not invent return-status semantics for this void function. After failed EBUSY Finalize, clear the prior diagnostic only in the test harness, query the still-live device, then Finish/finalize safely. Resource-inflight tests belong to the existing real queue qualifier; a host-only scalar test cannot claim device-busy behavior without creating real retained resources. These are proposed checks, not test results from this research.
